# P1-17 / P1-18 / P1-22 / P1-23 — WindowManager DX batch (v0.26.0)

Cztery powiązane tematycznie itemy z P1 dostarczone w jednej wersji 0.26.0.
Wszystkie dotyczą cyklu życia focusu i pętli render w `WindowManager`,
razem z drobnym rozszerzeniem Window o stacking order.

- **P1-17** — z-index stacking order na oknach.
- **P1-18** — focus management API (`focusNext/Prev/First/Last/ById/trapFocus`).
- **P1-22** — hooki `onFocus` / `onBlur` na Window.
- **P1-23** — error boundary w pętli render z callbackiem `onError`.

## P1-17 · z-index / stacking order

### API

```typescript
interface WindowProperties {
  zIndex?: number;   // default 0 — higher renders on top
}
class Window {
  getZIndex(): number;
  setZIndex(zIndex: number): void;
}
```

### Algorytm

`Window.render()` przestał rysować dzieci w zwykłej kolejności wstawiania.
Przed pętlą blitów woła prywatne `orderedByZ()`, które zwraca stabilne
sortowanie po `(zIndex asc, insertion idx asc)`. Dzieci z wyższym `zIndex`
rysują się **ostatnie** — czyli na wierzchu. Przy remisie trzymamy kolejność
`addChild()`, więc nic się nie zmienia dla istniejących layoutów, które nie
ustawiały `zIndex`.

Layout (flex / absolute / grid) pozostaje nienaruszony: `runLayout()`
nadal iteruje `this.children` w kolejności wstawiania, bo geometria nie
powinna zależeć od warstwy rysowania.

### YAML

`YamlWindowDef.zIndex` jest przekazywany 1:1 do `WindowProperties.zIndex`.

### Back-compat

Każde okno bez `zIndex` dostaje default 0, więc istniejące layouty renderują
się identycznie jak w 0.25.0.

## P1-18 · focus management API

### API

```typescript
class WindowManager {
  focusNext(): void;
  focusPrev(): void;
  focusFirst(): void;
  focusLast(): void;
  focusById(id: string): boolean;       // true = match found + focused
  trapFocus(within: Window): () => void; // returns release fn (LIFO)
  getFocusTrap(): Window | null;
}
interface WindowProperties {
  id?: string;   // used by focusById
}
class Window {
  getId(): string | undefined;
  setId(id: string | undefined): void;
}
```

### Algorytm

`focusNext/Prev` to cienkie wrappery na `moveFocus(+1/-1)`. `focusFirst/Last`
iterują aktywne `FocusEntry[]` od początku lub końca, szukając pierwszego
eligible. `focusById` przeszukuje aktywny kontekst (top-most dialog lub
main stack) po `Window.getId()`.

`trapFocus(within)` zapisuje referencję do Window w `focusTrap` i zwraca
funkcję-release. `isFocusable()` dokleja check `isWithinTrap(control)` —
descendant traversal po `Window.getChildren()`. `setFocus`, `focusById`,
`moveFocus` (cykl Tab) wszystkie przechodzą przez `isFocusable`, więc trap
automatycznie działa na każdej ścieżce. Funkcja-release przywraca poprzedni
trap (stacking LIFO), więc zagnieżdżone kompozyty są OK.

### InterfaceBuilder integracja

YAML `id:` (dotąd używany tylko przez zwróconą `Map<string, Window>`) jest
teraz również kopiowany do `WindowProperties.id`, więc `wm.focusById('btnSave')`
działa bez dodatkowej konfiguracji.

## P1-22 · onFocus / onBlur hooks

### API

```typescript
interface WindowProperties {
  onFocus?: () => void;
  onBlur?:  () => void;
}
class Window {
  setOnFocus(handler: (() => void) | undefined): void;
  setOnBlur(handler:  (() => void) | undefined): void;
}
```

### Algorytm

`Window.setFocused(focused)` jest teraz idempotent guarded — zwraca od razu,
gdy `this.focused === focused`. Przy prawdziwej zmianie odpalamy zapisany
handler (`onFocus` na `false → true`, `onBlur` na `true → false`). Ponieważ
każda ścieżka focusu w `WindowManager` (setFocus, moveFocus, focusById,
focusFirst/Last, initializeFocus) i ręczne `setFocused(true/false)`
przechodzą przez `Window.setFocused`, handlery fire'ują się raz i spójnie
niezależnie od źródła zmiany.

## P1-23 · error boundary w render()

### API

```typescript
interface WindowManagerOptions {
  onError?: (err: unknown, control: Window) => void;
}
```

### Algorytm

Nowy moduł-holder `ErrorHolder.mts` (analogiczny do `RegistryHolder`) trzyma
globalny `ErrorHandler | undefined`. `WindowManager` ustawia go w konstruktorze
(jeśli opcja została podana) i czyści w `stop()`.

`Window.render()` owija wołanie `child.render()` + `blitChild(child)` w
try/catch:

```text
for (const child of orderedByZ()) {
  if (!child.visible) continue;
  try {
    child.render();
    blitChild(child);
  } catch (err) {
    paintErrorPlaceholder(child, err);   // ⚠ render error: <message>
    const handler = getErrorHandler();
    if (handler) handler(err, child);
    else         throw err;              // no silent swallowing
  }
}
```

`paintErrorPlaceholder` alokuje świeży `Region` w obszarze dziecka, wypełnia
go stylem `foreground: 196 / background: 52 / bold` i wpisuje jednoliniowy
komunikat (prefix `⚠ render error: ` + przycięty `err.message`). Następnie
wykonuje `blitChild(child)`, żeby placeholder trafił do regionu rodzica
i nie zostawiał dziury. Jeżeli placeholder sam rzuci (np. błąd z
StyleRegistry), wewnętrzny try/catch go tłumi.

### Back-compat

Bez zainstalowanego handlera `Window.render()` rzuca wyjątek dalej jak
dotychczas — żadne istniejące testy ani konsumenci nie widzą zmiany,
dopóki nie podadzą `onError` w konstruktorze `WindowManager`.

## Przykłady

### Overlay dialog pinned on top

```typescript
const dialog = new Window({ pos: Pos.center(), size: new Size(40, 10), zIndex: 100 });
screen.addChild(dialog);   // zawsze nad resztą, niezależnie od kolejności addChild
```

### Programmatic save

```typescript
wm.bindKey('ctrl+s', () => { wm.focusById('btnSave'); return true; });
```

### Composite trap

```typescript
const release = wm.trapFocus(compositeRoot);
// Tab cycles only inside compositeRoot descendants
// …
release();
```

### Error sink

```typescript
const wm = new WindowManager(screen, {
  onError: (err, control) => logger.warn('render fail', control.getId(), err),
});
```
